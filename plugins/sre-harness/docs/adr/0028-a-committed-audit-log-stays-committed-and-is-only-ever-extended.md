# A committed audit log stays committed after gc, and is only ever extended

`audit.py commit` writes `audit/<id>.closed`, and every writer of an incident's audit log (the hook, `audit.py record`, the gateway's chat decisions and policy changes) refuses once that marker exists. `incident.py gc --apply` then deleted the marker with the rest of the incident's local state. From that moment the incident looked uncommitted: a session still pointing at it, a gateway approval, or a re-attach that issued a fresh bind token started a new genesis spool (homelabia#281; catalog-66 and catalog-28 on 2026-11-20 and 2026-11-21). Committing that spool failed on the timeline's pinned hashes with wording that read as data loss; `commit --offline` skipped the pins, found the audit branch gone after merge, and opened a pull request that would have replaced the merged log (sre-catalog#68, closed unmerged).

**gc leaves a tombstone.** Before deleting anything it writes `retired/<id>.json` with the committed log's record count and head. `audit_hook.is_closed()` is true while either `.closed` or the tombstone exists, so every writer that already respected the marker now respects it after gc too, with no new check at each call site. The tombstone is not incident state: gc does not assess it again and `release_active_marker` ignores it. It is a few hundred bytes and is kept indefinitely. Considered instead: keeping `.closed` (gc would keep finding and reporting the incident), and asking the audit repository from `is_closed()` (git in the hook's hot path, which must stay fast, standard-library only and offline).

**Post-commit work is refused, and reopen continues the log.** The refusal names `incident.py attach <id> --reopen`. Reopen removes `.closed` and the tombstone, restores the spool byte for byte from the audit repository's default branch if gc removed it, and appends a `reopened` record naming the length and head it continues. The chain stays one chain. Before this, `attach --reopen` of a committed incident left `.closed` in place, so the hook silently recorded nothing after a reopen. Considered: a fresh spool with a link record, committed beside the original or stitched at commit time; rejected for two chains per incident and stitching logic in commit.

**Commit only extends a merged log.** When `<id>.jsonl` is on the default branch, the spool must start with exactly those bytes, or commit refuses (`not overwriting an audit record`). `--offline` skips the timeline pins, never this. A continuation therefore lands as an append-only diff.

**A pin mismatch says what it is.** When a log's first record is a genesis record written after the pin it fails, `check_anchors` reports `a new chain started at <ts> (<n> records), after the timeline pinned <m> records at <at>`. Only a pin that already mismatches is reworded; a rewrite that keeps the original first record still gets the plain mismatch. The wording is not a defence: a hostile rewrite could forge a later first timestamp, and commit refuses either way.

**Leftover spools are dropped by a person.** `incident.py gc --incident <id> --discard-spool [--apply]` needs exactly one incident, a resolved one, and its committed log on the default branch with an intact chain matching every pinned hash. It prints every record it would drop, then retires the incident and deletes its local state. It is refused from chat, in the script and by a chat-policy deny rule. Dropped records are deleted, not kept: the printed list is the trace, and anything that matters can be recorded again after a reopen.

**Incidents cleared before the tombstone existed** are retired on `attach`: a resolved incident with no local state whose log is on the default branch gets a tombstone and no bind token. No migration step is needed.
